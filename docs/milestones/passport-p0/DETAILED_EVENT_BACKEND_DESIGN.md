# Proposed detailed-event backend — design only

This is a future tier for Opus's 1.3 client contract, separate from the deployed aggregate `passport_analytics.daily_counts` and its schema-1/schema-2 collector. No SQL here has been applied.

Use a private `passport_analytics.events` table with a surrogate row key, `event_id` UUIDv4 unique within the app, `install_id` UUIDv4, `session_id` UUIDv4, `event_name` from the [manifest](analytics_event_manifest_v1.json), `occurred_at` UTC, `received_at` UTC, `app_version`, `build_number`, `build_channel`, `device_layout`, `screen_id`, `control_id`, allowlisted `properties` JSONB, and `schema_version`. A canonical payload hash supports identical replay acknowledgment and conflicting replay rejection. Partition/index by received month and by `(build_channel, install_id, occurred_at)` only if real volume justifies it. No broad browser grants; use a service-only ingestion function and an aggregate-only read role for Kopa.

The collector validates the generated schema plus event-specific semantic rules, requires a bounded clock skew and batch size, and commits accepted events and batch acknowledgment atomically. Its response lists accepted, duplicate, and rejected event IDs with stable reasons; transport 200 never implies all events were accepted. Do not log payloads or identifiers. TestFlight/debug must be excluded from production reports at query level, not just a UI filter. Keep the current aggregate collector operating during migration; do not reinterpret its historical counters as detailed events.

Read-only Kopa queries should use mature install cohorts and explicitly show denominators and coverage: first launch → onboarding → first stamp; first-session time to stamp; picker/import abandonment; journey engagement; client purchase outcomes; D1/D7/D30 return sessions; layout comparisons. Session paths require ordered events within one session and a policy for missing session endings. Apple downloads, Apple Ads, website visits, and verified proceeds remain separate aggregate sources. No cross-source user join is available under this design.

Before implementation: owner/legal consent decision; retention/deletion policy; Opus client fixture compatibility; isolated collector replay/error tests; review of RLS/service grants; production backup/restore exercise; release-gated pilot in TestFlight; observed coverage and rejection dashboards; then a separate production approval. The proposed 45–90 day raw retention is a decision point, not an active setting.
