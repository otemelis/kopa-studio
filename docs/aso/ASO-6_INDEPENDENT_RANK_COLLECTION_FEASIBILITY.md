# ASO-6 — Independent iOS Organic Ranking Collection Feasibility

**Review date:** 17 October 2026
**Scope:** Research-only assessment for KOPA; no store searches, automation, scraping, vendor API calls, purchases, or production changes were performed.
**Decision:** A technically plausible independent collector is not currently supportable as a permitted, dependable KOPA data source. Keep organic position unavailable unless Apple authorizes the collection method in writing or a licensed provider grants adequate automated ingestion and retention rights.

## Finding

There are three different things that are often called “App Store rank”: the order rendered by a particular native App Store search, the ordered result array returned by a catalog-search interface, and a vendor’s reported rank observation. They must remain separate measurements. Neither Apple’s public catalog search nor the two open-source projects reviewed establishes the order shown in native iPhone search. AppTweak, AppFollow, and Appfigures sell useful country-scoped rank observations, but their public documentation does not establish that KOPA may operate an independent collection process or retain those observations for a product. The ranking layer already added to KOPA is a suitable replaceable contract; no collector or dashboard should be added until collection rights and source behavior pass validation.

Apple’s current Media Services terms state that users may not use software, a device, an automated process, or a similar/equivalent manual process to scrape, copy, or perform measurement, analysis, or monitoring of Apple Services or Content. The Germany-language terms contain the same restriction. Apple's website terms separately restrict automatic and similar manual monitoring of the website. This language appears to reach both unattended UI automation and a repeated human protocol whose purpose is to record keyword positions. That is a conservative reading of published terms, not legal advice. Ordinary personal browsing is different in purpose, but this project should not convert it into a measurement feed without Apple’s written permission or counsel’s specific clearance. [Apple Media Services Terms (Germany)](https://www.apple.com/de/legal/internet-services/itunes/de/terms.html), [Apple Media Services Terms (English)](https://www.apple.com/legal/internet-services/itunes/ms/terms.html), [Apple Website Terms](https://www.apple.com/legal/internet-services/terms/site.html).

## Method comparison

|---|---|---|---|---|

| **Apple Ads Search Terms / Impression Share** | Official account API exposes paid campaign/search reporting where eligible. | Not an organic position. Search Ads may occupy labeled placements in native results, including more than one slot; paid auction placement must be excluded from organic claims. | Account, campaign, date, country, reporting threshold and ad rotation constrain coverage. The existing KOPA evidence already records these as paid measures. | Read-only reporting is appropriate under existing authorization, but only as paid-search data. It cannot validate organic rank. Apple describes Search Ads placements in its [placement documentation](https://ads.apple.com/app-store/help/ad-placements/0082-search-results). |

Apple’s App Store search guidance says search can use app metadata and customer engagement/popularity signals, with suggestions and other result types. It does not publish enough of the ranking algorithm or session context to reconstruct every result from public metadata. This is why even a valid snapshot is scoped to surface, country, device and time, not a timeless rank. [Apple App Store Search](https://developer.apple.com/app-store/search/).

## Open-source projects reviewed

### shantj/asorank

The implementation calls `https://itunes.apple.com/search` with the query, country, `entity=software`, `media=software`, and a result limit. It finds the app’s `trackId` in the returned array and reports the 1-based index, or `None` if the app is outside the requested result depth. The code includes retries/backoff and tests for parsing and API behavior. Those tests show the implementation handles its endpoint contract; they do not compare synchronized results to native iPhone search. Its README explicitly calls the endpoint undocumented for this purpose and says native equivalence is not guaranteed. The README presents a live within-endpoint case study, not paired native ground truth. The repository is MIT licensed, but its method remains catalog order and its license does not authorize Apple-service collection. [Repository and stated caveats](https://github.com/shantj/asorank), [ranking implementation](https://github.com/shantj/asorank/blob/main/asorank.py).

### Aero25x/ASO-Copilot

Its iOS `findRank` calls the same iTunes Search endpoint with country/entity/limit, finds the bundle ID in `results`, and returns index + 1; absence becomes `null`. It also uses iTunes Lookup for metadata and scrapes product-page HTML for the subtitle. Its README describes daily tracking, but the public project does not supply paired native comparison evidence establishing the rank. Its keyword volume/difficulty are described as heuristics rather than real search volume. The repo’s MIT license covers its code; it does not confer Apple data rights. This is useful reference code for queueing, storage, retries and app identity, but its iOS positions should be labeled catalog-result positions rather than native organic observations. [Repository and method description](https://github.com/Aero25x/ASO-Copilot), [iOS provider implementation](https://github.com/Aero25x/ASO-Copilot/blob/master/src/lib/stores/appstore.ts).

Both projects demonstrate that KOPA can cheaply compute **catalog result index**. Neither demonstrates the product requirement in this study. KOPA’s current collector has the same basic behavior: it requests the first 100 catalog results and persists `position` derived from array order. Its stored values are legacy catalog observations, not verified native ranks. This report does not alter them.

## Vendor evidence and limitations

Vendor APIs are a possible path to licensed observations, not an independent KOPA-owned collector. Their product claims and APIs describe returned ranks, but the public materials reviewed generally do not reveal the exact device/account instrumentation used for every rank observation. Vendor output should therefore be labeled with vendor and method version, not asserted to be identical to a particular user’s native results.

| Provider | What public material establishes | What remains unknown for KOPA |
|---|---|---|
| **AppTweak** | API exposes current and historical app-keyword ranks, language/country/device fields, live keyword search endpoints, and a `fetch_performed` signal that can distinguish checked from no-fetch states. Its documented delivery schedule says followed keyword data is daily, with live fetches for newly followed keywords; its Ad Intelligence separately says it simulates keyword searches daily to detect paid ads. | Public rank docs do not fully specify the source-device/account population, how language is resolved, native-session agreement, result-depth limits for every endpoint, or whether KOPA may keep and use returned records in a product. Current self-serve terms and the intended commercial/product use require written confirmation. `value` must be separated from interpolated/effective values. [API current](https://developers.apptweak.com/reference/keyword-metrics-by-app-current), [API history](https://developers.apptweak.com/reference/keyword-metrics-by-app-history), [data schedule](https://help.apptweak.com/en/articles/9755509-data-delivery-schedule), [terms](https://www.apptweak.com/en/legal/terms-of-services). |
| **AppFollow** | Help material describes real-time search results and suggestions for selected keyword/country, top results “as they appear” in the store, plus tracked keyword positions by country and iPhone/iPad. The ASO API exposes app ID, keyword, country, device, date and position; API parameter material says positions are limited to Top 200 and has a separate below-Top-200 marker. Popularity may be Apple-provided in some territories and internally estimated elsewhere. | How ranking requests are physically collected; effective language/account/device conditions; refresh schedule and historical completeness for the API; per-keyword checked/unranked/failure distinction; exact automated ingestion, retention and onward-use rights. Public API use does not by itself settle rights under AppFollow’s current terms. [Keyword Tracking](https://support.appfollow.io/hc/en-us/articles/360020831817-Keyword-Tracking), [API endpoint](https://docs.api.appfollow.io/reference/keywords_api_v2_aso_keywords_get-1), [API parameters](https://support.appfollow.io/hc/en-us/articles/360020832317-API-Parameters), [terms](https://get.appfollow.io/terms). |
| **Appfigures** | `/aso` exposes tracked app/keyword rank trends and stats with country, iOS handheld/tablet device, date range and daily/hourly granularity (plan-dependent). API returns `position`; aggregate stats include an unranked-keyword count. | Public API reference does not document how a specific rank is collected, exact language/account context, per-keyword checked/unranked/no-data state, native-search calibration, or KOPA retention/product rights under a current agreement. An absent row or normalized value cannot safely be called checked-unranked without vendor confirmation. [Keyword Ranks API](https://docs.appfigures.com/api/reference/v2/aso-keyword-ranks), [API terms](https://docs.appfigures.com/api/terms). |

None of these public descriptions was verified against a live vendor response or native search during this research. Prior KOPA work established only the documented API shapes and candidate costs; no provider purchase, trial, credit use, or account inspection was made here. Any commercial agreement must explicitly permit scheduled API ingestion, storage duration, internal analysis, and display to the KOPA owner/team. If KOPA later becomes a multi-customer/commercial product, request rights for that exact use rather than assuming owner-only rights extend to it.

## Replaceable KOPA observation architecture

Keep the existing provider-neutral ranking contract and persist append-only observations. Add an adapter only after a permitted source passes validation. Every record should state:

| Field | Meaning |
|---|---|
| `app_store_id`, `keyword_exact` | Stable target app and exact submitted query; do not normalize away meaningful spelling/diacritics. |
| `storefront_country` | Storefront/market explicitly used by source, not device GPS. Preserve source-reported value. |
| `language_requested`, `language_effective`, `language_evidence` | Effective language may be `unknown`; do not infer it from country. |
| `device_family`, `device_model`, `os_version` | Provider-supplied device class or, for an authorized native observation, actual device/OS. Leave unknown fields null. |
| `surface` | `native_app_store`, `apps_apple_com`, `itunes_catalog`, or `provider:<name>`. Do not combine series across surfaces by default. |
| `observed_at`, `retrieved_at`, `timezone` | Source’s observation time, KOPA retrieval time, and timezone/precision. A historical backfill retrieved today is not a contemporaneous observation. |
| `position_surface`, `position_organic` | Ordered position on that surface versus organic position if the source explicitly classifies ads. Keep null if organic separation is unknown. |
| `result_depth`, `ads_detected`, `ad_classification` | Search depth and whether paid results were detected/removed; preserve unknown rather than guessing. |
| `state`, `reason` | `ranked`, `confirmed_unranked_within_depth`, `not_checked`, `unavailable`, or `ambiguous`, plus source reason. |
| `provider`, `provider_method_version`, `request_id`, `raw_evidence_hash` | Provenance and reproducibility. Keep any retained raw payload subject to provider rights and privacy policy. |

Rules: a positive integer position requires a successful observation; “unranked” requires explicit completion at a known depth and the app absent; timeout, empty response, rejected request, absent date, unknown depth or unclassified ad behavior is unavailable/ambiguous. Never turn absence into rank `101`, `201`, or `501`; never interpolate, carry forward, or overwrite an earlier observation. Keep vendor rank, catalog index and any authorized native-surface position in separate method/surface series. The existing contract in [`ranking-provider.ts`](../../apps/tools/src/lib/aso/ranking-provider.ts) already provides a base for provider-neutral raw observations; no code was changed as part of this feasibility study.

## Controlled validation protocol (conditional on authorization)

Do not execute this protocol until Apple gives written permission for the measurement activity or counsel confirms the proposed collection is permitted under the applicable terms. Do not change Apple Account regions to manufacture test markets; use devices/accounts already associated with the required storefronts. Apple describes app availability by storefront and account country/region settings; changing account country can affect billing, subscriptions and payment settings. [Availability by territory](https://developer.apple.com/help/app-store-connect/manage-your-apps-availability/manage-availability-for-your-app-on-the-app-store), [Apple Account country/region](https://support.apple.com/en-us/118283).

1. **Freeze scope:** published InnerType first; 5–10 exact terms; US and Germany; iPhone only; same test window, iOS version, device family, display language and account storefront where feasible. Record any condition that cannot be held constant. Add POIS only after its listing is public and indexed.
2. **Capture four separate surfaces:** (a) native iPhone App Store, (b) matching `/country/iphone/search` web result surface, (c) official iTunes Search API response, and (d) one vendor observation (Appfigures, AppTweak or AppFollow). Only run the Apple-facing measurement arms after permission; provider API access must also have explicit user approval and vendor retention terms.
3. **Record evidence:** exact query and submitted locale, result order/visible depth, app IDs, timestamp/timezone, storefront source, device/OS, query corrections, loading/errors, and sponsored labels. Keep sponsored and organic ordinals separate only when the source labels the ad. Preserve raw response or screenshot evidence only where rights permit. Do not infer a missing row as unranked.
4. **Repeat:** three captures in separate sessions on the same device/account, then repeat on a second existing device/account for the same storefront. The point is to quantify session/account variance, not to average away it. Repeat the matrix in the second storefront using a separate account already set to that territory.
5. **Analyze agreement:** compare exact app IDs and positions separately for each pair of surfaces. Report top-N recall, exact-position agreement, median absolute position difference, ads-classification agreement, and completion/missingness rate. Never name one surface “ground truth” for another. Pre-register any acceptance tolerance before seeing results; a starting decision threshold could be ≥90% of matched vendor/native observations within ±2 positions and ≥95% explicit completion-state coverage, while still reporting per-country results and variability.
6. **Decision:** if native repeatability is low, describe rankings as surface/session-dependent. If vendor/native agreement is low, the provider remains vendor-specific. If Apple permission or vendor retention rights fail, stop the corresponding collection route regardless of technical accuracy.

The protocol is a design only. No native, web, catalog, or vendor result was fetched for this report, and no claim about current InnerType position is made.

## Recommendation and unresolved dependencies

**Do not build an independently operated App Store ranking collector now.** Physical-device capture and UI automation could technically inspect a rendered native result list, but the current Apple terms make a purpose-built monitoring process unapproved on the evidence available. Public catalog search and OSS rankers do not meet native accuracy. Vendor APIs may provide the cheapest practical source of tracked positions, but source instrumentation and KOPA’s ingestion/retention rights remain contract questions.

The lowest-risk path is: (1) request written Apple guidance about an owner-operated, read-only keyword-rank measurement service, including human observation and XCUITest/Appium; (2) in parallel, ask one vendor (Appfigures first for price, AppTweak if an explicit checked/unranked/no-fetch contract is essential) to confirm exact collection scope, native-calibration evidence, country/language/device support, result depth, observation cadence/history, missingness semantics, API access and KOPA retention/display rights; (3) only after approval, run the bounded comparison above; (4) choose a source only if the permitted data matches the product’s required claim. AppFollow may remain a comparator. Continue Apple Ads and App Store Connect on their own measurement tracks.

Still unknown: Apple’s written interpretation for this specific use; App Store’s exact backend relationship between native, web, iTunes catalog and Ads results; native automation’s actual App Store accessibility behavior on supported iOS versions; each vendor’s concrete collection fleet/sampling, per-observation completion semantics, and agreement against native results; and written retention/redistribution rights under the current KOPA product model. These are evidence gaps, not assumptions to fill with scores.
