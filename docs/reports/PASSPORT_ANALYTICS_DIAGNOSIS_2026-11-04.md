**Read-only audit: 4 November 2026. No live app, database, Vercel, or Apple configuration was changed.** This updates the earlier [early-signals snapshot](PASSPORT_EARLY_SIGNALS_2026-11-04.md), which ended before Apple's 3 November reports appeared. **Why Kopa missed Apple Analytics.** Apple confirms one approved `ONGOING` PASSPORT report request (`1a1002c3-3a07-4d10-afca-6352b89790d5`). Kopa's `aso_analytics_report_requests` has **no PASSPORT mapping row**. The existing `syncDiscoveryAnalytics` auto-discovers only the approved POIS request, then iterates mapped requests; its first-time-download import is also explicitly POIS-only. The live maintenance summary reported successful storefront import for *mapped* apps, which masked the absent PASSPORT coverage. This is an importer coverage gap, not an Apple report-generation gap. The importer reads only the first 50 report-catalog entries: PASSPORT Discovery happened to be entry 49 in today's response, so catalog pagination should be added before relying on it. The Kopa website panel uses the Vercel project `meetpassport` and a server-side token; the production environment variable is present. Its actual rendered value and browser presentation were not inspected in this audit.

**Reconciliation boundary.** The official **52 Sales units** and **36 Analytics first-time downloads** on “3 Nov” are *different metrics and date systems*; a 52-to-36 subtraction is not an identified error or lost-user count. Downloaded Sales reports use **Pacific Time**; Analytics uses **UTC** and its 3 Nov rows may be revised. Apple also notes processing and definition differences. Sales PTI `1` means first-time app units under the Apple Account definition, while Analytics `First-time download` is the report's download type. Kopa's generic Sales parser currently aggregates all matching app rows without a PTI filter; keep its label “Sales report units” until the proposed import validates PTI/SKU and separates app units, redownloads and in-app purchases. Never label Sales units as device first opens or unique people. Website UTC days and PASSPORT device-local event days are separate again.

## Proposed privacy-preserving app event contract

**No retroactive reconstruction.** Current aggregate counts remain historical aggregates. Add event-level collection only for future opted-in/authorized builds after privacy review; do not fabricate old installation IDs.

| Part | Minimal contract |
| --- | --- |
| Envelope | `schema_version`, immutable `event_id` (random UUID), `install_id` (random app-scoped UUID), `session_id` (random UUID per foreground session), `event_name`, UTC `occurred_at`, server `received_at`, `build_channel` (`appstore`/`testflight`), app version/build, coarse device layout (`standard`/`folded`/`unfolded`/`unknown`). No IDFA, IDFV, account ID or website visitor ID. |
| Installation and session | Generate `install_id` once per app installation in app-container storage; a reinstall starts a new identity. Generate a session ID at foreground start and persist it with the queued events so recovery preserves it. `install_started` is observable first launch, not an App Store download; `session_started`/`session_ended` have an explicit inactivity rule and recovered-session state. |
| Core milestones | Reuse `onboarding_completed`, `first_stamp_completed`, `stamp_created`, `journey_opened` and existing sharing events. Add one-time `third_stamp_completed` and `fifth_stamp_completed` based on a local stamp count, with no stamp content or destination. Allowed collection enum: `country`, `us_state`, `airport`, `park`, `unknown`; reuse existing event names where present and add only missing collection-specific milestones. |
| Journey, import, DLC | Keep low-cardinality `journey_opened`, `journey_shared` (when actual share completion is observable), `import_started`/`import_succeeded`/`import_failed` with a coarse failure code, and `dlc_viewed`/`dlc_purchase_started`/`dlc_purchase_completed_client`/`dlc_restored_client` with a fixed product enum. Never send imported itinerary contents, filenames, receipt contents or transaction IDs in analytics properties. Reconcile *verified* purchases separately through Apple's official reports or a separately approved transaction-verification path. |
| Retention | Cohort = install UTC date of the first accepted `install_started`; activity = at least one accepted foreground `session_started` on exact UTC day +1, +7 or +30. Count distinct `install_id` once per cohort/day; show only mature denominators (D30 requires 30 elapsed days plus upload grace). Define a separate rolling-window return metric if useful; never relabel it D7. Internal/TestFlight cohorts are excluded from customer retention. |
| Delivery | Persist event ID and payload in a bounded offline queue before upload; retry with the same IDs. Server unique constraint on `(app_id, event_id)` and transactional batch acknowledgement; replays with changed payload reject. Enforce event-name and property allowlists, clock-skew bounds, schema version, channel and version validation. Track accepted/rejected counts, upload age, lag and coverage. Keep the existing schema-2 aggregate receipt protection until the new path is approved and proven. |

Use collection **type**, never country/state/airport/park identifiers, precise coordinates, travel dates, names, notes, photos or free text. Store no personal itinerary in analytics. Suggested raw-event retention is the shortest period that supports D30 plus late-upload correction (for example 45–90 days after privacy review), with aggregate cohorts retained separately and a deletion/reset path for the random install ID. A random identifier is still potentially personal data when it supports longitudinal profiling. Before release, review the privacy policy and App Store privacy labels for identifiers and product-interaction data, the applicable EU consent/ePrivacy basis, and whether any cross-company sharing would trigger ATT. Do not use ATT as a substitute for the broader privacy review.

## Smallest implementation sequence for review

1. **Apple reporting first, no app release.** In a local branch, extend the existing importer to recognize the already-approved PASSPORT request ID (no new Apple request). Import Discovery and Downloads Standard with app-ID/schema/segment checksum validation and latest-`processingDate` replacement **per `Date`**; never sum overlapping instances. Preserve source type, page type, territory, report date, processing date and source provenance. Import/reconcile 29 Oct–3 Nov as a bounded backfill only after local dry-run checks. Track per-app expected-vs-imported coverage so “success for other apps” cannot hide PASSPORT. For Sales, make report date explicit and catch up missing complete days; validate exact ID, SKU and PTI. Kopa dashboard can then show Apple impressions, product-page views, first-time downloads and source breakdowns, each with its own freshness and completeness state. This requires a separate production-data-write/deployment approval.
2. **Website read validation.** Keep the current read-only Vercel integration. Add a source-status check and reconciled period/date labels; use referrer *page views* as a breakdown and show blank as unknown. If the project has multiple domains, label the project scope unless a supported hostname filter is validated. No website-to-install or Reddit-to-download attribution claim.
3. **App event slice, after privacy and release approval.** Add the minimal envelope/queue and future-only events in the PASSPORT app, plus a private event table/ingest path scoped to PASSPORT. Test offline replay, duplicate IDs, lost acknowledgements, recovered sessions, channel separation, invalid properties, delayed upload, consent off/on and deletion. Show installation/session distinct counts, event-level funnels and mature D1/D7/D30 cohorts only after reconciliation against controlled device runs. Keep the current aggregate dashboard during transition; do not silently reinterpret it as user data.
4. **Purchase verification.** Keep client DLC events as interaction signals. Show paid conversions/revenue only after Apple Purchase/Sales coverage or server-side StoreKit transaction verification is validated against official totals. Do not attach Apple aggregate purchase rows to individual app journeys.
