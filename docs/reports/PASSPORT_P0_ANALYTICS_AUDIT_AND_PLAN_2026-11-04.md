# PASSPORT P0 analytics: verified state and Kopa plan

Read-only audit, 4 November 2026. This builds on [the established diagnosis](PASSPORT_ANALYTICS_DIAGNOSIS_2026-11-04.md). No PASSPORT repository file, production database, Apple configuration, or deployment was changed.

## What shipped and what is observed

| Evidence | Finding |
| --- | --- |
| PASSPORT `Passport/App/Analytics.swift`, `docs/ANALYTICS.md`; commits `86969d8`, `38da678` | The initial specification implemented 77 typed, allowlisted semantic events, local daily counters and a debug inspector. Uploads were initially off. `38da678` enabled anonymous completed-day count uploads and a Settings opt-out. This is a count pipeline, not an event stream. |
| `Passport/App/Analytics.swift` `Analytics.track`, `AggregateCounter`, `AggregateUploader` | Calls are serialized to a utility queue and duplicate callbacks within 0.4 s are suppressed. Counts are grouped by local day/event/coarse dimensions, kept on-device for up to 35 days and uploaded in completed-day batches on foreground opens, at most every six hours. `app_opened` and `app_backgrounded` are recorded, but no persistent session ID or `session_ended` exists. The local `analyticsInstallDay` supports a coarse `first_use` flag; it is not an uploaded installation identity. |
| PASSPORT commits `81f4648`, `d8a0df1` | Later source added immutable schema-2 batch retry tokens and validated acknowledgments. The receipt is a **batch** identity, not a person or session identity. Verify the actual released build before assuming these fixes reached App Store users. |
| PASSPORT `release/1.0.1`, `release/1.1`, current `feature/beyond-borders`; commits `6ca1105`, `b59e9d2`, `8f2fe55` | The branch history adds 1.1 interactions, then 1.2 Parks/Flight Log and purchase-funnel events. Source presence does not prove App Store release. Current Supabase rows show App Store **1.0 only**, TestFlight 1.0, 1.0.1 and 1.2; no observed 1.1 or App Store 1.2 rows. Version labels are client-reported; they do not by themselves prove exact binary commit. |
| Read-only Supabase `passport_analytics` schema | Physical tables are `daily_counts` and `upload_receipts`; other relations are aggregate views. `daily_counts` columns are day, build channel, app version, event, dimensions, count, updated time. `upload_receipts` stores batch ID/hash/count/time. There is no event-level table or install/session identifier in this schema. This does not establish whether an unrelated external system has private events. |
| Read-only production rows | App Store 1.0: 401 aggregate rows, 1,505 event counts, 29 Oct–3 Nov. TestFlight is separate: 1.0 (156 rows), 1.0.1 (35), 1.2 (89). Event counts are **interactions, not people**. |

Existing production events include onboarding presentation/completion, first stamp, stamp picker/editor activity, stamp creation and milestones, cover and page turns, journey and sharing, library/collection activity, purchases/restores, layout changes and errors. Import tracking in the current code is primarily **backup restore** (`backup_restore_tapped/finished`) and photo suggestions; a staged CSV selection/preview/cancel/success/failure funnel is not established. Purchase completion is a **client signal**, not verified revenue. `share_sheet_opened` is not proof that a share completed. See the [event contract](PASSPORT_P0_EVENT_AND_BACKEND_CONTRACT_2026-11-04.md) for exact reuse/add decisions.

Because the server receives only pre-aggregated counts, it cannot order events for one installation, calculate first-session elapsed time, count distinct users across steps, reconstruct abandoned paths, or form exact mature D1/D7/D30 cohorts. The local days-since-install bucket can show a distribution of **opens** but cannot supply a retained-install denominator. No historical IDs should be synthesized.

## Apple reporting gap and Kopa implementation order

The approved PASSPORT Analytics request `1a1002c3-3a07-4d10-afca-6352b89790d5` exists at Apple, but Kopa has no mapping. Kopa's `api/aso/_lib/appstore-analytics.js` discovers only POIS and imports Downloads only for POIS. The report catalog fetch is limited to one 50-entry page. Latest-processing-date selection is present and must be retained. On 4 Nov Apple had 3 Nov PASSPORT first-time downloads **36**, impressions **104**, product-page views **82**, and Sales **52 app units**; Kopa had no PASSPORT Analytics rows and Sales ended 2 Nov. These figures have different definitions/time zones and are not a funnel. See the established diagnosis for source breakdowns and website reconciliation.

1. On a Kopa development branch, map only approved ongoing request IDs to known Apple app IDs; discover/read reports without creating requests. Paginate report catalogs, daily instances and segments with finite page/instance limits; fail on unexpected host, checksum, app ID, report schema or malformed date. Retain all source-type and territory rows and processing-date provenance.
2. Backfill only an explicit, bounded reporting interval after a local dry run. Select the latest processing version **per report Date**, not the latest four files globally. Re-import revisions idempotently by app/date/country/source; validate that stale keys removed by a revision are handled before production use. Coverage must identify each expected app/report/date as available, zero, partial, pending or error. A successful POIS import must not conceal PASSPORT absence.
3. Keep Discovery impressions/page views, Downloads Standard first-time downloads, Sales units, Apple Sessions, website visits and client events in separate source series. Do not rename Sales units as downloads. Sales catch-up needs explicit report dates and Apple PTI/SKU validation. Apple Sessions need a separate metric contract before any retention display.
4. Test local fixtures for multi-app mapping, pagination, corrected partitions, source breakdowns, missing reports, late revisions, gaps and no-write dry run. Compare summed imported rows by exact report date/territory/source against downloaded Apple files. **Production deployment and reporting-row writes require separate approval.**

### Local implementation checkpoint

The Kopa development branch `codex/passport-analytics-recovery-2026-11-04` now has a local importer candidate: exact POIS/PASSPORT approved-request mapping, bounded catalog/instance/segment pagination, a 35-instance ceiling, an optional explicit 35-day report-date interval, per-request coverage result, first-time-download source rows, and a no-write `dryRun` option. The 73 `api/aso/_lib` tests pass, including new mapping/pagination/window tests. **It has not been deployed or run as a production backfill.**

Two release blockers remain before a live import: (1) obtain and reconcile a bounded dry-run result against official PASSPORT files in the current Apple reporting window; (2) handle rows that disappear in a later Apple revision, because ordinary upsert updates present keys but leaves obsolete keys. The existing importer already chooses latest processing date for rows it sees, but must not be called fully revision-safe until this removal case is handled and tested. The Sales importer still fetches only the latest available report and does not filter PTI; it is outside this local patch and its catch-up requires a separate reviewed change. The Apple Sessions report is not yet imported. These are explicitly unavailable Kopa capabilities, not zeros.

## Kopa reporting and quality gates

Show an acquisition strip by Apple report day: impressions, product-page views, first-time downloads and source-type breakdowns, each with source, processing time, coverage and timezone. Show Sales units separately in Pacific Time. Website visitors/page views/referrer hosts remain Vercel project aggregates; blank referrer is unknown. The first-party app panel keeps aggregate counts explicitly labeled until future event-level collection is proven. Do not render a cross-source person funnel.

After a future app-side release and private event ingest are approved, add *separate* user-flow views: acquisition-to-first-launch (aggregate bridge only), first-launch→onboarding→first stamp for observed installations, first-session path/time, picker and CSV import abandonment, journey and sharing, DLC exposure→client outcome, mature D1/D7/D30 cohorts, and regular/Duo layout segments. Every rate needs a defined same-install denominator, chronological horizon, sample size, channel/version filter and completeness state. Apple downloads cannot be linked to anonymous app IDs without a valid attribution mechanism. See [Opus handoff](PASSPORT_IOS_OPUS_HANDOFF_2026-11-04.md).

## Privacy/release gate

An app-scoped random install ID still permits longitudinal profiling and can be personal data. Before shipping event-level collection, review the actual privacy policy, App Store privacy declarations, GDPR lawful basis, EU ePrivacy/consent implications, retention/deletion and opt-out behavior with qualified counsel. No names, travel history, precise destinations/locations, dates, notes, photos, filenames, arbitrary text, IDFA/IDFV or cross-app IDs. Do not change the 1.2 build under Apple review. Current aggregate collector and privacy behavior remain intact until a separately approved replacement is validated.
